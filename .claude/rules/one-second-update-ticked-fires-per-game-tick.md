# `OneSecondUpdateTicked` is one real second only on our SMAPI build — stock SMAPI fires it every 60 game ticks

Stock SMAPI raises `GameLoop.OneSecondUpdateTicking`/`Ticked` on every 60th update tick, which is one real second only at the stock 60 ticks/sec. The server pins the tick rate to `SERVER_TPS` (`ServerOptimizer.cs` sets `Game1.game1.TargetElapsedTime = 1000/Env.ServerTps` ms), so at the proven-stable `SERVER_TPS=5` stock SMAPI fires the event every **12 seconds**. The images ship a source-patched SMAPI (`patches/smapi/0001-derive-one-second-divisor-from-tick-rate.patch`, built by the Dockerfiles' `smapi-builder` stage) whose divisor is derived from `TargetElapsedTime`, so on the server and the test-client the event fires once per real second at any TPS. The mod must still stay correct on stock SMAPI, so treat the cadence as "at least one second, up to 60 ticks": latency-sensitive **sequential** handlers (stepping a multi-box cutscene, anything where each invocation unblocks the next) go on `OnUpdateTicked` with their own gating.

**Why:** The wedding-host "play-through" attempt drove dialogue-clicking from `OnOneSecondUpdateTicked` and took ~70s (watchdog-tripping) because, on stock SMAPI at `SERVER_TPS=5`, the handler fired every 12s — confirmed in the server log (clicks exactly 12s apart). The cadence is a method-local `% 60` in `SCore.OnPlayerInstanceUpdating`, unreachable from mod code (see [`harmony-patch-reachability.md`](harmony-patch-reachability.md)), which is why the fix is a SMAPI source patch. `GameManagerService.RunHealthCheck` counts fires of this event down from `HealthCheckSeconds`, so on stock SMAPI its routine probe ran hourly instead of every 5 minutes. ([`server-tps-headless.md`](server-tps-headless.md) establishes 5 is the stable headless TPS; this rule is the orthogonal "what that does to per-second handlers" trap.)

**How to apply:** When adding or moving a host-automation handler, ask whether its latency matters. If it just reconciles a one-shot state and a multi-second delay would be acceptable, `OnOneSecondUpdateTicked` is fine. If it must fire promptly or step a sequence, put it in `OnUpdateTicked` (per-tick — fires reliably even when in-game time is frozen, which is why the festival and wedding handlers live there) and do any "once per N seconds" gating yourself off wall-clock (`DateTime.UtcNow`) or a tick counter scaled by `Env.ServerTps` (e.g. `BannerDelaySeconds * Env.ServerTps`), never off the `OneSecond` cadence. When a `OneSecond*` handler looks slow in a log, check which SMAPI is running (`smapi-internal/.sdvd-smapi-build` in the game volume holds the image's build id) before theorizing.

## The loop's second trap: one-shot writes parked there lose races

A host write that should apply exactly once per save (a new-game choice, a one-shot world-state stamp) must run from the deterministic `AlwaysOn.OnSaveLoaded` pre-seed path (`PreSeedEarlyGameEvents`/`PreSeedChoices`), not from this loop. On the loop the write **races any other writer of the same field** (a `/test` seed, an operator command, the engine) and silently overwrites whichever landed first. The pre-seed path runs synchronously inside `SaveLoaded`, which the `/reload` and `/newgame` completion contract waits on (`GameManagerService` resolves the completion `Task` on the first `UpdateTicked` *after* `SaveLoaded`), so the value is settled before the operation returns and before anything else can touch it.

**Why:** `AlwaysOn.HandleCaveChoice` set `caveChoice` from `OnOneSecondUpdateTicked`, guarded only by `!eventsSeen.Contains("65")` (no idempotency latch). `SaveImportTests.Import_SwapHost_CarriesMasterGatedState` seeds `caveChoice=1`; whenever the automation pass fired *after* the seed but before `"65"` was present, it re-applied the server's mushroom default (`2`) over the seeded value → ~33% flake (`Expected 1, Actual 2`). The fix moved the choice into `PreSeedChoices()` called from `OnSaveLoaded`, removing the timing dependence entirely.

**How to apply:** For a host-side write that should happen once per load, ask "could another writer (a test seed, a command, the engine's own day-start) touch this same field in the window after load?" If yes, put it on the `OnSaveLoaded` pre-seed path — don't park it on this loop with only a mutable-game-state guard. Keep the single-shot signal save-persisted (`eventsSeen` membership, object existence) so a `/reload` re-run of the pre-seed is a clean no-op. Latency-sensitive *sequential* handlers still belong in `OnUpdateTicked` per the section above; this section is about one-shot writes something else can race.
