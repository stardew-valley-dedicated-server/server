# Verify named claims before publishing them

Before you write a concrete claim that a reader will act on — an identifier name, a framework behavior, a cited number, a "nothing consumes this" cut, "the reference implementation handles X" — verify it. One grep, one source read, one benchmark check. Don't pattern-match plausible-sounding names from context, don't propagate cited numbers without checking the primary source, and don't act on shallow no-consumer reads.

**Why:** A fabricated `SDVD_STEAM_ACCOUNTS_N` (real name: `STEAM_ACCOUNTS`) almost shipped in a user-facing log message, pattern-matched from the surrounding `SDVD_MAX_*` convention without a grep. Every category below has its own near-miss: a "30-50% slower under emulation" figure that conflated Rosetta (~20%) with QEMU (~85%); a `correlation_id` cut that would have broken `AsyncLocal` capture (`asynclocal-pitfalls.md`), one of 6 wrong calls in a batch of 11; `JsonlReporter` risks that applied equally to the already-shipped `InfrastructureEventLog`; a spec whose "serves any N workers" motivation contradicted its own disjoint-slicing design, which would have led an operator to undersize `STEAM_ACCOUNTS`.

**How to apply:**
- **Identifier names** in plans or proposed user-facing strings (env vars, flags, file paths, Makefile targets, config keys, event names) → one Grep before publishing. Especially important for strings that survive the plan and outlive it (log messages, error text, doc snippets).
- **Cited numbers** from secondary docs ("~30-50% slower", "transfers in seconds", polling cadences) → check the primary source (vendor docs, measured benchmark, the actual code path) before depending on the figure.
- **Values you invent** (timeouts, caps, limits) → size from a quick measurement of the real operation, not a defensively large guess. A hook timeout picked as 600s measured at 9-25s; 120s was right.
- **"Nothing consumes this" cuts** → grep the identifier project-wide and read every hit, not just the count. Qualified approval ("when you're sure", "if it makes sense") means verify per cut, not per batch.
- **"In-tree pattern is risky" framing** → check whether the reference implementation faces the same risk. If it does and it's fine, the risk is either unreal or already accepted, so it can't block the change. Save the concern for what actually differs: lifecycle scope, call-site patterns, shared state.
- **Framework internals** (xUnit dispatch, SMAPI events, Stardew save flow) → read `decompiled/sdv-1.6.15-24356/` or vendor source. Don't reach for "I think X works like…".
- **How .NET behaves in an edge case** → write a few lines, run them against the project's .NET version, and take that output as the answer. Probe before the claim reaches a plan, not after it's questioned. Behaviour that shifted between .NET Framework and modern .NET is the highest-yield case to check: a disposed cancellation source does NOT make `HttpClient` throw on net10.0 — that token behaves like a live one.
- **"Only N call sites are affected"** → establish where the enclosing scope ends, then open every helper it calls and follow it to its implementation. Grep the receiver name to gather candidates, then confirm each by reading; helper indirection is where the real count lives.
- **Design docs with separate "why" and "how" sections** → one explicit cross-check pass. Take each concrete claim from the motivation (numbers, scaling, "serves any N", "bounded by X") and confirm the implementation delivers exactly that property. Drift between the two sections is a load-bearing bug because readers act on the motivation.
- **Identifiers being introduced by this change** are exempt — they're new by definition and there's nothing to verify against.
