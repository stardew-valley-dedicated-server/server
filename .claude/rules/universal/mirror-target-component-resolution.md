# A probe that detects another component's state must mirror that component's full resolution logic

When you write detection code that models another component's behavior — "is this container configured the way the real X would interpret it?", "what would the runtime resolver decide?" — the model must mirror the target's complete resolution order, not just the path you happen to be familiar with. Picking only the happy path produces silent false negatives: the probe says "no conflict" while the target component is actively in the state you were trying to detect.

**Why:** The Steam-account conflict probe (`ExtractUsernamesFromEnv` in `tests/JunimoServer.Tests/Containers/SharedSteamAuth.cs`) read only `STEAM_ACCOUNTS` from inspected container env — but the real sidecar (`DiscoverAccounts`, `tools/steam-service/Program.cs`) tries `STEAM_ACCOUNTS` JSON *first*, then falls back to legacy `STEAM_USERNAME`, and production deployments use the fallback by default (`docker-compose.yml`). The probe's partial model never saw their username: tests passed the probe, then collided at runtime with `LogonSessionReplaced`. Fix: mirror the JSON-first/legacy-fallback resolution step-for-step.

**How to apply:** When the detection code's job description is "predict what component X would do with this configuration," open X's resolver and read it end-to-end before writing the probe. Specifically: list every input X consults, every fallback chain, every "if A is set use A, else use B" branch — your probe must implement all of them or it will under-detect. Unlike the claim-verification rules, this is about *modelling another component's logic* — the probe must reproduce the target's full resolution path, not sample it. Put a comment in the probe naming the source-of-truth file and symbol so the next reader knows to re-sync if the target's resolution order changes.
