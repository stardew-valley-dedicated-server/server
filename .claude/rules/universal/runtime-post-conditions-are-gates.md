# Runtime evidence outranks plan claims — post-conditions, fix predictions, and root-cause hypotheses are all gates

When a plan's post-conditions read as runtime observations — "X returns…", "Y works end-to-end against…", "Z appears in the output" — those are *gates*, not aspirational text. Static review (`dotnet build`, `grep` that references are gone, reading the diff) does not satisfy them. Run the thing and observe the result before reporting complete. This outranks the plan's own claims: a received plan's prediction ("Change 1 drops the failure rate") is a claim to verify against runtime data, and if the data contradicts it the task isn't finished — investigate further, even outside the original scope.

**Why:** Plan `02-jsonl-reporter-deletion`'s post-conditions named a runtime check ("`make test-events` returns phase-decorated rows"); a static sweep (build clean + zero refs + diff coherence) was passed off as done, and the pushback-forced runtime walk surfaced two real bugs in a jq filter transcribed verbatim from the plan: it crashed on null `displayName` and never matched (names are fully-qualified `Namespace.Class.Method`). Twice more, caught only by pushback: a recording-pipeline plan whose fix-prediction was the wrong premise (runtime ffprobe showed the `finalizedSegments=0` rate had *risen*, not fallen — root cause upstream in the recorder's host-start timing), and a *diagnosis* plan where a 2-minute `CLIENT_FPS=10` experiment would have falsified the load-bearing root-cause hypothesis before ExitPlanMode. Distinct from `plan-discipline.md` (verifying a plan's claims *before* ExitPlanMode); this is verifying *outcomes*.

**How to apply:** At "all done?", re-read the post-conditions verbatim. For each, classify: static fact (compiles, refs gone, file exists) → build/grep/read confirms it; runtime observation (returns X, works against Y, appears in Z) → actually run it on real data and inspect. A user-facing recipe (Make target, CLI, query) doubles as its own smoke test. If a runtime check genuinely costs more than ~2 min (full E2E, multi-host) and you can't run it, say so explicitly — "post-condition X not exercised, needs <cost>" — rather than implying via silence that all were checked.

**One gate earlier — the edit must be IN the artifact before you verify its behavior.** A green build doesn't prove your source change reached the binary: when a pipeline `COPY`s conditionally (a multi-stage Dockerfile copying a subset of the tree, a solution including only some `.csproj` outputs), your edit can target a file the artifact never consumes — the build stays green because the consuming stages didn't change. An edit to `docker/rootfs/etc/services.d/xvnc/run` passed a green `make build-test-client` that never COPYs that tree; a full plan-and-implement cycle was lost. Spot-check the produced artifact directly (`docker create <tag>` + `docker cp <id>:<path> -`, `MSYS_NO_PATHCONV=1` on Git Bash; `unzip -p` / `dotnet build --verbosity normal` for packaged outputs), especially when build cache is involved, multiple Dockerfiles/assemblies pick selectively from one tree, or you haven't personally verified the consumer relationship.
