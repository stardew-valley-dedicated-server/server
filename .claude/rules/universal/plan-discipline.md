# Plan discipline: adversarial pre-verification, cross-step invalidation, announced edit counts — and delete the plan when its code lands

On any non-trivial multi-step plan: include adversarial self-verification *in the plan* before calling ExitPlanMode, re-read the whole plan for cross-step invalidation before coding, in review cycles match your edit count to what you announced, execute every item, and retire the plan document when its work merges.

**Why:** Recurring failure patterns, each caught only by user pushback:
- **Verification-after-pushback.** First plan rejected with "are you 100% confident?"; I verify, resubmit, approved. The verification was always needed — upfront saves the round trip.
- **Cross-step invalidation.** In the VNC retained-phase plan, step 2b changed the data flow so disposed instances stayed in `state.instances`, but step 2 still claimed they moved to `stoppedInstances`; faithful execution shipped a regression (the "Open VNC" link on torn-down containers).
- **Silent edit-count creep.** Announced 4 review-fix items, made 5 edits (an unannounced compatibility-scope disclaimer); the user had to audit the diff. Silent creep in a sign-off cycle forces full re-verification.
- **Implemented-but-retained plans.** An audit found nine implemented plans still in the tree, months old, status headers reading "open" for shipped work. Two were nearly kept purely because their runtime gates hadn't been exercised — over-extending `runtime-post-conditions-are-gates.md`, which blocks *claiming done*, not *retiring the document*.

**How to apply:**
- **Adversarial self-verification.** For any refactor touching shared infrastructure (sleep, warp, auth, lobby, netReady, day transition, save flow), include a "Compatibility verification" section in the plan covering: LAN vs Steam transports, lobby/unauthenticated players, test TPS (`SERVER_TPS=5`), FPS caps, disconnect-mid-operation, stuck-latch recovery, other subscribers to the same events. Cite file:line. If something can't be verified read-only, say so explicitly rather than skipping it.
- **Cross-step pre-read.** Before starting implementation on any plan with 3+ interacting changes, do one adversarial read-through asking: "does any later step invalidate a claim or assumption in an earlier step?" If yes, surface it in the plan or adjust before coding. Skip on small plans; always do it on plans that touch multiple components with data-flow changes.
- **Match edit count to what you announced.** When responding to review feedback with a list of N fixes, make exactly N edits. If a 5th issue surfaces mid-fix, either fold it into an existing item with a note, or stop and announce it ("also spotted X — adding that too, OK?") before applying. Applies specifically to review/iteration cycles where the user has signed off on a scope; not to open-ended "clean this up" asks.
- **Check off every item.** When implementing a multi-item plan, address EVERY item before declaring completion; after finishing, re-read the plan and verify each item landed.
- **Delete the plan when its code lands.** A merged plan is dead weight: `git rm` it in the same change, then grep its filename across `.claude/` and `docs/` and repair the citations. The test for "landed" is whether the artifacts the plan proposed exist in the tree — never the plan's own status header, which is written before merge and not updated after. A genuinely part-done plan keeps only its outstanding parts. Verification gates the plan listed but nobody ran are a reason to run them (or file an issue) — never a reason to retain the document.
