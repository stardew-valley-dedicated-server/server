# An "improvement" claim needs a controlled same-config A/B, not a comparison against plan numbers

To claim a change *improves* something (faster, cheaper, fewer allocations) — as opposed to merely *works* — measure baseline vs branch on the **same host, same env/config, same inputs**, changing only the code. The baseline is the parent commit built and run yourself, not a number quoted from a plan doc, a prior run at a different commit, or a run at a different config. "It works and my run is faster than the plan's stated baseline" is not evidence of improvement.

**Why:** Asked whether a wedding-test speedup was "actually an improvement," I reported a delta by comparing my run against the *plan document's* baseline figures — which had been captured at a different commit AND a different `SERVER_TPS` (5 vs the 60 I'd run at). The user pushed back: "Have you compared comparable runs?" The comparison was invalid on two axes at once (commit + config), so the "improvement" was unfounded. The honest measurement required a detached baseline worktree at the parent commit (`git worktree add --detach <parent>`), an identical `.env.test` copied from the branch worktree, both reset to the CI-proven `SERVER_TPS=5`, run baseline-then-branch on the same host. Only then did the −32% ceremony / −23% test-body delta become a defensible claim — and the baseline reproduced the plan's stated numbers exactly, which is what *validated* the setup as comparable.

**How to apply:** Before asserting a perf/efficiency win, ask "what exactly am I comparing against, and does it differ from my run in more than the code?" If the baseline is a plan's projection, a run at a different `SERVER_TPS`/`CLIENT_TPS`/FPS, or a different commit — it's not comparable; go build the real baseline. Control every variable but the code: same host (per `test-timing.md`, parallel wall-clock is noisy — prefer an isolated metric like a single test's body duration or a per-primitive span over total suite time), same committed config at the proven-stable value (`server-tps-headless.md`), same inputs. A quick sanity check that the setup is sound: does the baseline reproduce the previously-known baseline numbers? If not, the comparison is still mis-controlled. Distinct from `runtime-post-conditions-are-gates.md` (verify a change *works* by running it) and `diff-flaky-runs-before-theorizing-mechanism.md` (diff pass/fail artifacts of a *flaky* test): this rule is about proving a *directional improvement*, which needs a matched baseline the other two don't require.
