# An "improvement" claim needs a controlled same-config A/B, not a comparison against plan numbers

To claim a change *improves* a measured runtime property (faster, cheaper, less GC pressure) — as opposed to merely *works* — measure baseline vs branch on the **same host, same env/config, same inputs**, changing only the code. A statically provable delta (a `new` deleted from a loop, a call eliminated) needs no benchmark; this rule covers claims only a measurement can support. The baseline is the parent commit built and run yourself, not a number quoted from a plan doc, a prior run at a different commit, or a run at a different config. "It works and my run is faster than the plan's stated baseline" is not evidence of improvement.

**Why:** Asked whether a wedding-test speedup was "actually an improvement," I compared my run against the *plan document's* baseline figures — captured at a different commit AND a different `SERVER_TPS` (5 vs my 60). Invalid on two axes at once; the user pushed back ("Have you compared comparable runs?"). The honest measurement was a detached worktree at the parent commit (`git worktree add --detach <parent>`), identical `.env.test`, both at the CI-proven `SERVER_TPS=5`, baseline-then-branch on the same host — only then was the −32% ceremony / −23% test-body delta defensible, and the baseline reproducing the plan's stated numbers is what *validated* the setup as comparable.

**How to apply:** Before asserting a perf/efficiency win, ask "what exactly am I comparing against, and does it differ from my run in more than the code?" If the baseline is a plan's projection, a run at a different `SERVER_TPS`/`CLIENT_TPS`/FPS, or a different commit — it's not comparable; go build the real baseline. Control every variable but the code: same host (per `test-timing.md`, parallel wall-clock is noisy — prefer an isolated metric like a single test's body duration or a per-primitive span over total suite time), same committed config at the proven-stable value (`server-tps-headless.md`), same inputs. A quick sanity check that the setup is sound: does the baseline reproduce the previously-known baseline numbers? If not, the comparison is still mis-controlled. Unlike `runtime-post-conditions-are-gates.md` ("it works"), a *directional improvement* claim needs this matched baseline. If the matched A/B genuinely isn't affordable, say so and state the improvement as unmeasured — never imply it ran.
