# Don't hedge with empty scaffolding — either build the holistic solution or mark a clear TODO

When a task calls for a "clean and consistent" or holistic solution, don't ship half-built scaffolding to *imply* the missing piece will arrive later. If something must genuinely be skipped, leave a TODO that names the gap concretely — not a comment that softens the omission ("future work", "consumers may want this", `field = []` placeholders). Either complete the piece, or be explicit that it's missing and why.

**Why:** Caught twice in one session: a proposed `ctrf-report.json` merge with `results.tests = []` plus a "future work" comment would have silently misrepresented the report as containing no tests; then general user pushback: "Don't skip anything if it's needed for a clean and holistic solution. IF we skip something, leave a clear TODO." Artifacts that *look* complete carry hidden gaps a downstream consumer won't notice until they hit the missing data.

**How to apply:** Before shipping an empty placeholder field, an empty array stub, or a comment like "future" / "for now" / "consumers may want", ask: does this look complete to the next reader? If yes and it isn't, either build it or omit the field entirely so the gap is visible. When you must skip, write `// TODO:` with the concrete missing thing — what's not implemented, what would be needed to implement it, what the current behavior gives instead. The inverse bound: a TODO is only justified for a concrete gap in *this* change. Never leave a TODO or comment about a hypothetical feature that doesn't exist in the tree (a `TODO(distributed): when a multi-worker coordinator lands…` was rejected — no coordinator exists); if something is a verified non-issue, leave nothing. Distinct from `simplest-solution.md`'s "verify a consumer before adding scaffolding" (that rule says cut unbacked features); this one covers what to do when the feature is genuinely needed but you can't finish it now.
