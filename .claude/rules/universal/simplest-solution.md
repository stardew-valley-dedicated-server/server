# Prefer the simplest, most direct solution

If the fix is to remove a line, remove it. Don't add a redirect, wrapper, or abstraction layer. If the codebase already has a pattern for something, follow it exactly.

**Why:** Four failure modes around scaffolding and abstraction:
- **Over-engineering when a one-liner works.** Reaching for a "flexible" wrapper when the repo already has a working pattern, or when deleting the line is the actual fix.
- **Building infrastructure with no consumer.** A planned discovery API plus display-name porter existed to seed per-test entries in `ctrf-report.json`; every reader — Makefile, LLMRenderer, UI, GitHub Actions, FlakinessTracker — touched only `results.summary`. Cutting it saved ~320 lines.
- **Dissolving an established home for a convention.** Inlining the last method of `Helpers/AssertHelpers.cs` into its single caller would have removed the home for custom asserts in a codebase that keeps accumulating them. "Re-extract when the next one arrives" doesn't happen: the next assertion lands somewhere new and the pattern fragments.
- **Reflex-rejecting a consolidation the user asked for.** Two sibling handlers shared the same accidental placement on a racy loop; folding both into one `PreSeedChoices()` home was refused twice as scope creep, on the strength of a stale adjacent comment. Reading the method plus `git log` settled it in minutes — the placement was accidental and the move was safe.

**How to apply:**
- **Default to the simplest fix.** Before proposing a wrapper, redirect, or new abstraction, check whether an existing function or pattern already does this. If the simplest fix feels too small, it's usually right.
- **Verify a downstream consumer before scaffolding.** When a refactor proposes new infrastructure to *feed* something — per-test entries in a report, extra event fields, a new index — grep for an actual reader first.
- **Pattern continuity beats consumer count.** The consumer check applies to *new* infrastructure only. An existing home for a convention (`*Helpers`, `Asserts`, `Validators`) whose membership has shrunk to one still earns its keep — plural name, single-concern namespace, siblings that suggest more will accrete. Keep the home and add to it.
- **Treat a user-proposed consolidation as work, not creep.** Folding sibling code together is consistency work. Resolve the one real question — does the moved code still work at the new call site? — by reading what it touches, plus `git log` for whether the old placement was designed or accidental. Decline only if reading shows a dependency the move breaks, and name it. Scope creep is the *silent* addition during a signed-off review cycle ([`plan-discipline.md`](plan-discipline.md)); a consolidation the user asked for is the opposite.
- **Count the existing sites before calling your own code's shape a defect.** Grep how many places already use the pattern you want to abstract away. If it's the house convention, keep it and say so — an abstraction at one of five sites leaves the codebase less consistent, not more. Change every site or none.
- **"Simplest" means simplest that meets the *stated* constraints.** Where the user has declared a constraint — perf, GC, latency, security — the qualifying solution is the simplest that satisfies it, not the fewest lines ignoring it. On game-thread mod hot paths the allocation-minimal version is that solution ([`mod-game-thread-allocation.md`](../mod-game-thread-allocation.md)). Applies only where the constraint is declared and the code is on the hot path — not a licence to optimize speculatively.
