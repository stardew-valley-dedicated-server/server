# Adversarial review must split findings, and keep the claim when only the framing was weak

Self-review fails in three shapes. **OOS-as-cover:** everything is labeled either inherent non-issue or out-of-scope, and OOS ships small bugs sitting right there. **Recommendation collapse:** pushback dents your framing and you withdraw the underlying claim with it. **Verdict-by-fiat:** the split is honest, but you close the deferrals with dispositions only the user can issue.

**Why:**
- **OOS-as-cover.** A review listed seven "non-issues"; splitting them on request revealed three real bugs minimized as OOS — one `volatile`, one missing `base.DisposeAsync()`, ~10 lines of eager run-id seeding. All small, all adjacent, all would have shipped.
- **Recommendation collapse.** A proposed rule merge was withdrawn entirely once review found its token-saving argument thin. Only the argument was thin; the merge was right, and the user had to ask for it back.
- **Verdict-by-fiat.** A CI-diff review closed five deferrals itself as "acceptable" or "consistent-by-design". Re-presented as open decisions with fix costs, all five turned out to be cheap fixes the user wanted made. Accepted is a state the user creates.

**How to apply:**
- **Split findings.** Label each inherent non-issue or OOS deferral. For inherent, name the guarantee that makes it safe — if you can't name one, it isn't inherent. For OOS, name the fix cost: lines, files, whether investigation is needed. Small and adjacent means fix it in this task.
- **Measure a gap against the fix's own premise, not the prior broken state.** When a change claims X is now the source of truth, a path that skips X breaks that claim even while being no worse than before. "Not a regression" is a valid deferral only when the gap doesn't contradict what the fix set out to establish.
- **Hand deferrals back as decisions.** For anything you won't fix in-task, give the finding, the mechanism, the fix cost, and a recommendation — then let the user rule. Watch for "accepted", "fine as-is", "consistent-by-design", "will confirm itself" appearing in your own prose with no decision behind them. Then actually pose the questions: enumerate them with options or use AskUserQuestion. Parking them in a doc gives the user nothing to answer.
- **Label each finding reachable or latent.** *Reachable* names the path that hits it; *latent* names what you checked to rule one out. Lead with that label rather than a severity word — it's what the ship/no-ship call rests on, and "fragile" or "not maintainable" without it lands as a shipped defect. Covers the case the split above misses: real mechanism, nothing reaches it.
- **Separate framing from claim.** When review weakens your own recommendation, ask which part it weakened. Weak framing → restate it sharper and keep the claim. Weak claim → drop it. Withdrawing both together is OOS-as-cover in a different coat.
- **In fan-out → verify → synthesize, don't let a binary filter drop verified sub-findings.** A `REFUTED` parent takes real sub-claims down with it — an overstated headline can carry a true dead-code claim in its evidence. Have the verifier emit salvaged sub-findings even on `REFUTED` verdicts and feed those to synthesis; reserve ranking slots for small high-confidence wins that `lines × confidence` crowds out; re-verify the raw finding set afterwards, since synthesis only ever saw what the filter passed ([`subagent-findings-are-claims.md`](subagent-findings-are-claims.md)).
