# Adversarial review must split findings, and keep the claim when only the framing was weak

Self-review fails in three shapes. **OOS-as-cover:** everything is labeled either inherent non-issue or out-of-scope, and OOS ships small bugs sitting right there. **Recommendation collapse:** pushback dents your framing and you withdraw the underlying claim with it. **Verdict-by-fiat:** the split is honest, but you close the deferrals with dispositions only the user can issue.

**Why:**
- **OOS-as-cover.** A review listed seven "non-issues"; splitting them on request revealed three real bugs minimized as OOS (a `volatile`, a missing `base.DisposeAsync()`, ~10 lines of eager run-id seeding) — all small, adjacent, and about to ship.
- **Recommendation collapse.** A rule merge was withdrawn entirely when review found its token-saving argument thin. Only the argument was thin; the merge was right, and the user had to ask for it back.
- **Verdict-by-fiat.** A CI-diff review closed five deferrals itself as "acceptable"; re-presented as open decisions with fix costs, all five were cheap fixes the user wanted made. Accepted is a state the user creates.
- **Latent-as-license.** An autocomplete review split honestly but shipped its latent findings as "note only" dispositions and padded the report with an inherent non-issue; the correction established both defaults — a reported finding gets fixed when the fix is cheap, and verified non-issues are cut, not reported.

**How to apply:**
- **Split findings — then every item is fixed, cut, or handed back; there is no "noted" bucket.** An inherent non-issue is one whose safety guarantee you can name — if you can't name one, it isn't inherent. Naming the guarantee is your *verification step*, not report content: once named, cut the item from the report entirely, because a verified non-issue in the findings list is noise the reader must re-triage. Everything that survives is a real finding with a fix cost (lines, files, whether investigation is needed) — small and adjacent means fix it in this task, and anything else goes back to the user as an open decision. "Fixed", "cut as inherent", "handed back" are the only three exits.
- **Measure a gap against the fix's own premise, not the prior broken state.** When a change claims X is now the source of truth, a path that skips X breaks that claim even while being no worse than before. "Not a regression" is a valid deferral only when the gap doesn't contradict what the fix set out to establish.
- **Hand deferrals back as decisions.** For anything you won't fix in-task, give the finding, the mechanism, the fix cost, and a recommendation — then let the user rule. Watch for "accepted", "fine as-is", "consistent-by-design", "will confirm itself" appearing in your own prose with no decision behind them. Then actually pose the questions: enumerate them with options or use AskUserQuestion. Parking them in a doc gives the user nothing to answer.
- **Label each finding reachable or latent — the label prices urgency, never whether to fix.** *Reachable* names the path that hits it; *latent* names what you checked to rule one out. Lead with that label rather than a severity word — it's what the ship/no-ship call rests on, and "fragile" or "not maintainable" without it lands as a shipped defect. But latent is not a deferral category: a latent finding with a cheap fix gets fixed in this task like any other, because the cost of leaving known debt in the tree exceeds the cost of the fix. Covers the case the split above misses: real mechanism, nothing reaches it *yet*.
- **Separate framing from claim.** When review weakens your own recommendation, ask which part it weakened. Weak framing → restate it sharper and keep the claim. Weak claim → drop it. Withdrawing both together is OOS-as-cover in a different coat.

## Review as a multi-agent workflow: right-size the launch, batch the verifiers, salvage refuted sub-findings

- **Right-size the launch.** Input that fits one context (a ~1k-line diff, one file, one document) gets reviewed inline — a workflow buys nothing there, even when a skill or effort level suggests one. When a workflow IS warranted, estimate worst-case agent count (producers × findings-per-producer) before launching; many-dozens means restructure first. A run downsized mid-flight can resume via `resumeFromRunId` — completed producers return from cache.
- **Batch the verifiers.** Default to ONE batch verifier per producer (indexed verdicts over all its findings, depth proportional to severity), not one agent per finding. Reserve per-finding fan-out for an explicit user ask ("verify each independently", a stated token budget).
- **The REFUTED-filter trap.** A binary filter between verify and synthesize drops true sub-claims with their overstated parent — an inflated headline can carry a real dead-code claim in its evidence. Have verifiers emit salvaged sub-findings even on REFUTED verdicts, reserve ranking slots for small high-confidence wins, and re-verify the raw finding set afterwards, since synthesis only ever saw what the filter passed ([`subagent-findings-are-claims.md`](subagent-findings-are-claims.md)).

**Why (workflow shapes):** A docs-audit workflow ran one verifier per finding and was heading past 100 agents before the user stopped it mid-run; rebuilt with one batch verifier per review area (~27 agents total), verification quality held — zero refuted-in-error, so the ~8× agent multiplier had bought no measured gain (ultracode/effort settings raise thoroughness, not the multiplier). Separately, an adversarial review of a single ~800-line diff was launched as a workflow at all; stopped mid-run ("stop going overkill on the agents") with partial results unrecoverable, the inline review that replaced it finished in comparable wall-time.
