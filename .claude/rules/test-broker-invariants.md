# Test broker invariants

Load-bearing invariants for the test resource broker, capacity gating, and session reuse. Re-introducing any of these has historically re-broken the suite.

## Capacity & Deadlocks — DO NOT

- **DO NOT release capacity between KeepConnected tests** — causes container deadlock AND exclusive deadlock. Sessions hold capacity for entire class duration.
- **DO NOT re-add `WaitingCount` eviction in `ReleaseAsync`** — causes server ping-pong at `MaxServers=1` (15 restarts, 20min vs 6.6min). The fix is `WaitForServerAvailableAsync` blocking without holding resources. (`WaitingCount` IS read live in `TestResourceBroker.cs` for a *post-create* eviction — that's a different site and stays. The rule is specifically about adding it back to `ReleaseAsync`.)
- **DO NOT use `[TestServer(Exclusive = true)]` on classes sharing a server with KeepConnected** — deadlock: KeepConnected holds ref, exclusive can't drain.
- **DO NOT re-add client pre-warming in `ManagedServer`** — races with `LeaseClientAsync`, creates duplicate clients. `ClientPool` handles creation-on-demand.
- **DO NOT take a second Steam-required client lease inside one test, and DO NOT re-add `WithSteam` to helper leases.** Once any Steam-bearing client exists, Steam-required leases queue on its return instead of creating another (`ClientPool.LeaseClientAsync` cold-start gate) — treat the Steam-bearing client as a scarce singleton. Lease the Steam primary (`GetClientAsync`/`Connect.*`) BEFORE any helper client: a non-Steam lease can take the Steam-bearing client as bag fallback, leaving a later Steam-required lease blocked mid-test (`ClientPool_LeaseSteamWait` with `availableInBag:0` is the tell). Helper leases (`LeaseClientForHelperAsync` → `ConnectSecondFarmerAsync`) are `requireSteam:false` by design — the second farmer joins via LAN; inheriting the server's `WithSteam` once made a test deadlock against its own primary and wedged the whole run.
- **DO NOT mint a second steam server config.** Each host slice's allocator partitions off ONE server account (`SteamAccountAllocator` index 0; slice-local per `SteamAccountSlice`) — a cost-minimization policy (Steam accounts are paid), not an infra limit; more concurrent steam servers need more steam-capable host slices. On a single-slice run, a `WithSteam` test that also overrides any server-config field (`StartingCabins`, `MaxPlayers`, password, …) forks the config; the forked config's prestart then blocks forever in `AllocateServerAsync` and the stall watchdog aborts the run with 0 tests executed (`steam_account_pool_insufficient kind=server` in `infrastructure.jsonl` is the tell). Steam tests use plain `[TestServer(WithSteam = true)]` + `SharedAssembly`, uid-scoped assertions, no `/newgame`. `AllowIpConnections` is forced true for ALL test servers (`ResourceRequirements.FromAttribute`) for the same reason — mixed-transport tests must not fork the steam config to get a LAN listener; the production IP-off posture is exercised via the runtime `/test/set_ip_connections` toggle (vanilla gates per connection attempt at `LidgrenServer.cs:152`, so the flag IS the door).
- **DO NOT park a Steam-required lease on the cap/patience/return waits when `PoolHasAnySteamBearingClient()` is false** — no return can ever satisfy it (bag, leased, and in-flight are all covered by that check), so it must route straight to the self-heal cold-start create in `LeaseClientAsync` (`steam_client_selfheal`). The route may transiently exceed `_maxContainers` by one; that's bounded by the Steam client slice and preferable to the run-stall deadlock it replaces (seen in CI: the sole Steam client died at lease cleanup, the next Steam lease parked at the cap forever).
- **DO NOT move the `_creationsInFlight` bump back inside `ReplaceServerInBackgroundAsync`** — `OnServerPoisoned` increments it atomically with the queue reset *before* scheduling the replacement (the callee's `finally` decrements; same caller-bumps/callee-decrements split as the `CreateAndResolveAsync` spawn sites). A late bump after the dispose-drain re-opens a ≤`PoisonDrainTimeout` window where the on-demand predicate sees `inFlight==0` on a reset queue and spawns a duplicate same-key creation — two live Steam servers then race for the single server account and the loser wedges holding a host server slot. `PoisonServer`'s one-shot gate is part of the same invariant: without it, two racing poison sources double-invoke `OnServerPoisoned` and schedule the duplicate anyway.
- **`SharedClass` does NOT serialize a class's test methods — xUnit v3 runs them concurrently** against the one shared server (confirmed in `TestLifecycle.cs`: "xUnit v3 starts all test instances within a class concurrently"). `SharedClass` only governs *server lifetime/reuse*, not method ordering. Tests coexist fine when they partition the world (distinct tiles/cabins), but a class whose methods mutate **shared global game state** — the calendar (`SetDate`/`SetTime`), `Game1.whereIsTodaysFest`, a singleton service's fields — will have its methods clobber each other's state. Add `[TestServer(Exclusive = true)]` at the class level to serialize them: class-level Exclusive makes each method wait for the prior via `_exclusiveClassTurn` (`ManagedServer.cs`) and holds the gate between methods so another class can't `/newgame` the shared server mid-test. (Only `KeepConnected` otherwise serializes a class — via a per-class turn lock — but it's for a different reason and conflicts with Exclusive per the rule above.)

## Test Infrastructure

- **Capacity is per-host, not global.** There is no global capacity gate — each queue carries the priority + settle-window semantics, multi-host runs gate per-host, and single-host runs route through `HostPool.Instance.First`. Host-record structure, per-host reuse caches, and `StartLimiter` sizing are canonical in [`docker-test-resources.md`](docker-test-resources.md).
- **`MaxClients` for config hash is test demand, not host slot count.** `host.ClientSlots` is a *scheduling* knob; `StartingCabins` derivation is unchanged. Tests still declare `clientsNeeded` via `[TestServer(...)]` and the broker enforces capacity per host.
- **Host disconnect cascades a class's tests — by design.** When a host fails a transport-class call (broken pipe / connection reset / daemon-socket gone), `HostPool.Place` filters it out for new placements and the cascade self-labels as infrastructure. Re-placing the class on a different host would defeat the no-auto-retry rule and silently mask the disconnect.
  - **Labeling (three seams):** `DockerHost.Poison` emits the `host_disconnected` event (with `sshMasterLogTail`) → `summary.json.infrastructureErrors`; the active test's failure record is stamped `failureCategory: "infrastructure"` (`TestBase.RecordTestFailure`); broker-waiting tests fail with `ServerUnavailableException`, which classifies `"infrastructure"`. A `KeepConnected` session pinned to a poisoned host fails the rest of that class the same way (N-test cascade).
  - **One classifier:** `TransportFaultClassifier.Classify`, consulted at both mid-run creation seams via `DockerHost.PoisonIfTransportFaultAsync` — server creation (`TestResourceBroker.CreateAndResolveAsync`) and on-demand client leasing (`ClientPool.CreateClientGuardedAsync`).
  - **Bare `TimeoutException` is ambiguous** (slow-but-live server vs dead tunnel) and only poisons when corroborated by a failed `ssh -O check` against the host's master (`TunnelManager.IsMasterAliveAsync`, remote hosts only) — do NOT "simplify" this into poisoning on every timeout, or a slow server cascades healthy tests. `-O check` probes master-process liveness, not tunnel liveness, so it has a bounded (~30s, self-healing) false-negative window for the bare-timeout-while-master-still-alive case; a genuinely dead forward throws `SocketException`/`HttpRequestException`, which the classifier catches directly without corroboration.
- **The `-f`-forked SSH master's `-E` log must use `LogLevel=INFO` and only captures the silent-timeout drop.** OpenSSH's "Timeout, server not responding" line (the `ServerAliveCountMax`-exceeded drop) is `LOG_INFO`, so `LogLevel=ERROR` suppresses the one line the `-E` log exists to capture — use `INFO`. Capture is drop-mode-dependent: a silent/timeout drop lands in `-E`, but an abrupt RST reaches **neither** `-E` nor a shell `2>>` (the `-f` fork reparents the child's stderr). So `-E` is silent-timeout-focused; the RST case surfaces as a `SocketException` the classifier catches directly — don't expect the fd-2 redirect to rescue it.
- **Mass `server_acquire_retry_after_transport_fault` + `test_skipped_infrastructure` may be an app crash, not transport.** A server whose app dies at startup without tripping the fatal-log scan (SMAPI-prefixed `ERROR|FATAL`, unprefixed `Process terminated.`) surfaces as the 75s daemon-responsiveness `TimeoutException` ("daemon-socket forward wedged?"), which the classifier treats as recoverable — heal → retry once → skip, repeated for every test in the run. Before suspecting tunnels, read `containers/server-N/container.log` for a crash the scan didn't recognize. (A .NET FailFast ran a full suite through this loop until the scan learned its pattern.)
- Each host's `StartLimiter` bounds concurrent Docker container starts on that daemon (sizing chain in [`docker-test-resources.md`](docker-test-resources.md)). Poison releases pending waiters. Three priority bands: **High** (server starts), **Normal** (on-demand client leases), **Low** (client pre-warm). Highest-priority waiter wins on every release; FIFO within a band. **No preemption** — a High waiter cuts the queue but cannot evict a slot already held by a Low waiter, so worst-case server-start contention with a full Low queue is bounded by the slowest in-flight pre-warm. Prestart fans out servers and pre-warm concurrently; the priority bands prevent a starvation where a flood of clients held all limiter slots past the server's `StartupTimeout`.
- `Release()` drains the queue synchronously. Separate release + reacquire is NOT atomic — other waiters get served in between.
- **A test that intentionally leaves its server unusable must retire it** by calling `Lease.Managed.PoisonServer(reason, ManagedServer.PoisonReasonCode.TestRetiredServer)` at end-of-test. `ServerPool` excludes poisoned servers from reuse (`IsPoisoned` checks at every selection site), and `OnServerPoisoned` boots a fresh instance for the next demand — so a later test (or another class under `SharedAssembly`) never inherits the damaged one. Required when a test breaks reachability irreversibly: the Galaxy outage test cuts the NIC, and on remote hosts `docker network connect` gives the container a new IP while the daemon never restores the published-port forwarding, so the API stays dark for any reuser (a 30s `ServerReady` timeout — surfaced only in the full suite, where the second method reused the server). `PoisonServer` is orthogonal to stopOnFail (it does NOT cascade-cancel — `_stopOnFailNotified` is set only by `NotifyStopOnFail`), and there is precedent: `TestLifecycle.PoisonOnCleanupFailureIfNeeded`, `PersistentSession`. Poison LAST, after all asserts: it cancels the `ErrorToken` — and lease cleanup still runs client ops after that (title navigation, fallback disconnect). Those must run on cleanup-scoped tokens (`TestLifecycle.RunCleanupCoreAsync`, `ClientLease.DisposeAsync`), never on the client's ambient `ErrorToken` binding: a poison-canceled token aborts the disconnect of a perfectly healthy client, `MarkClientDead` retires it, and when it was the pool's only Steam-bearing client that costs a full replacement boot (and, pre-self-heal, deadlocked the run at the container cap).

## Session Liveness

- **A liveness gate must cross-check client belief against server truth.** `PersistentSession.IsAliveAsync` originally only checked the test-client's `IsConnected` flag. The client can believe it's connected after the server has evicted the peer — reuse then proceeded and `GrantAdmin` failed for 10s with "player not found" (`getAllFarmers()` didn't contain the uid). Any "is this session still usable?" check that reads only one side of the connection is not a liveness gate. Require both: client-side `GetState().IsConnected` AND server-side `WaitForPlayerByIdAsync(uid)` within a short budget (`SessionRevalidationBudget`, 2s).
- **`/players` snapshot ⇔ `getAllFarmers()` for connected peers.** Both derive from `Game1.otherFarmers` — `/players` iterates `otherFarmers.Roots` via `FarmerCollection`, and `getAllFarmers()` filters `farmhandData` by `isActive() == otherFarmers.ContainsKey(uid)`. So `/players` is a reliable precondition gate for any `getAllFarmers()`-based mod endpoint.

## Polling Budgets

- **Outer polling budget must be ≠ the inner per-request timeout, or retries are impossible.** `TestTimings.PollingRequestTimeout` (5s) is a *per-HTTP-request* guard inside helpers like `ServerApiClient.WaitForPlayerByIdAsync`. Passing it as the *outer* polling timeout means a single slow request eats the whole budget — zero retries. Define a separate outer budget (e.g. `SessionRevalidationBudget = 2s` mirrors `FarmerRemovalBudget = 2s`) sized for the happy path on a cached endpoint (`/players` responds in <50ms). Inner and outer timeouts live next to each other in `TestTimings.cs`; easy to mix up.

## Server Config Keys

- **`config-{hash}` keys identify reusable servers.** Same config produces the same server key, regardless of `SharedAssembly` vs `SharedClass` lifetime — the broker reuses an existing matching server.
- **Config hash inputs**: password, starting cabins, farm type, max players, allow IP connections, Steam authentication, cabin strategy. Changing any of these splits the cache.
- **`Clients` does NOT split the cache.** It is excluded from the hash, and `StartingCabins` — which is in the hash — defaults to `Math.Max(4, HostPool.Instance.Hosts.Max(h => h.ClientCapacity.Capacity) * 3)` (`TestServerAttribute.cs`), i.e. host client capacity, *not* the test's `Clients` value. So two classes requesting different `Clients` share one server unless something else in the hash differs. Only an explicit `StartingCabins = N` splits it.

## Diagnostic Snapshots

- **Snapshot/diagnostic reads of contention state must be racy-but-pure reads.** When adding a snapshot delegate that reads state for an event payload (refcount, queue depth, available slots), the read must NOT acquire a lock the wait path itself holds (deadlock risk) and must NOT read non-thread-safe collections concurrently. `SortedSet<T>.Count`, `List<T>.Count` guarded by an external lock — both unsafe to read outside that lock. Safe alternatives: `ConcurrentBag<T>.Count`, `Volatile.Read(ref _intField)`, `volatile` fields, or plain value-type reads (racy but won't crash; "approximately right" is acceptable for diagnostics). Caught during design of wait-tracing snapshots: a proposed `queueDepth = Waiters.Count` would have read a `SortedSet<Waiter>` guarded by `ClientCapacity.Lock` from outside that lock — concurrent with `Add`/`Remove` it could throw or return garbage. Same shape applies to `_allClients.Count` in `ClientPool` (guarded by `_allClientsLock`). Snapshot delegates additionally must have no side effects.

**Why:** Each invariant is a real bug we hit and engineered around. The capacity rules were the most expensive — `WaitingCount`-eviction caused 20-minute runs at `MaxServers=1` until the wait-without-holding fix; `[TestServer(Exclusive=true)]` + KeepConnected deadlocked on the first attempt to combine them. The session-liveness gate was added after `GrantAdmin` failed for 10s in `getAllFarmers()` because the client believed it was still connected.

**How to apply:** When editing broker, `ClientCapacity`, `ClientPool`, `ManagedServer`, `PersistentSession`, or `TestTimings`, walk the relevant section above first. Especially before "simplifying" any of the DO NOT rules — the apparent simplification is the bug being warned against.
