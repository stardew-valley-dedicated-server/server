# Treat type 11 text and type 9 slot-list timing as the whole pre-join surface — there is no input channel and no durable LAN identity

A vanilla client parked at `FarmhandMenu` pre-join (gameMode 0; `serverHost`/`chatBox`/`currentLocation` all null) was swept against every SDV multiplayer message type (`Multiplayer.cs:46-115`), and each usable lever traced through the client's draw/menu/timeout code. Full result — don't re-run the sweep or hunt for hidden levers:

- **Type 11 `connectionMessage` — the only free-form server-controlled text, and custom text always shows the asset prefix.** The client does `connectionMessage = Game1.content.LoadString(payload)` (`Client.cs:128-129`). `LoadString` is `LoadStringReturnNullIfNotFound(path) ?? path` (`LocalizedContentManager.cs:570-573`), so an unknown *key* returns the payload verbatim — but the path must survive two earlier throws: `parseStringPath` throws when the payload contains **no colon** (`:692-701`), and `Load<Dictionary<string, string>>(assetName)` throws when the part before the first colon isn't a real string-dict asset (`:515`). So `"Strings\UI:<your text>"` renders `<your text>` behind a visible `Strings\UI:`, while a *real* key renders clean but fixed vanilla text. The prefix **can't be hidden and the block can't be raised**: SpriteText clamps draw-x to `>= 0` (`SpriteText.cs:520-532`), and `LoadGameMenu.drawStatusText` anchors the block's top at the viewport vertical center (`LoadGameMenu.cs:998-1005`; `y` is the top, `SpriteText.cs:124-127`). Only message length and `^` line breaks are yours — `SpriteText.cs:642` strips `Environment.NewLine`, which is `\r\n` on a Windows client, so a bare `\n` isn't stripped either and won't break a line.
- **Type 9 `availableFarmhands` — the slot list, and a one-shot latch.** `FarmhandMenu.checkListPopulation` rebuilds slots only while `gettingFarmhands || approvingFarmhand` (`FarmhandMenu.cs:154-195`). A status-only hold (no type-9) leaves `approvingFarmhand=true`, so a later *first* type-9 repopulates cleanly — but any **non-empty** type-9 flips both latches false (`receiveAvailableFarmhands` always builds a non-null list, `Client.cs:150`), after which further type-9s update the model and never rebuild the visible slots. Nothing server-side re-arms the latch; only a user slot-click (which commits a join) or a fresh menu (reconnect) does. **So showing a mock slot and later revealing real slots without a click are mutually exclusive** — pick one.
- **Type 23 `forceKick` — the only message that drops a held client.** An unjoined client has no farmerId, so `kick` can't reach it. `receiveForceKick` reads no payload and runs `Disconnect(Kicked) + returnToMainMenu()` when `!Game1.IsServer` (`Multiplayer.cs:1513-1520`), routed through the client's default message case — transport-agnostic, just a message to the connection. Left alone, a hold ends at the client's own **45s** timeout: `Client.connectionTimeout = 45000` ms (`Client.cs:12`), armed at connect (`:84`), cleared only by `receiveAvailableFarmhands` setting `hasHandshaked` (`:163`), then `DisconnectType.ClientTimeout` (`:95-100`).
- **Type 1 `serverIntroduction`** forces the client into gameMode 3 without a slot pick — powerful but half-initialized and crash-prone.
- **Dead positive levers (verified against `Game1.cs`):** type 20 achievement — `getAchievement` early-returns on `gameMode != 3` (`Game1.cs:10619`); type 21 global/HUD message — the HUD draw block is gated out at gameMode 0 (`Game1.cs:13791`); chat (10/15) and join/leave info are hard-guarded by `Game1.chatBox != null`. Everything else is a guaranteed NRE (types 4, 8, 13, 14, 16, 17, 19, 25, 29 deref `serverHost.Value`/`SourceFarmer`/null location/`teamRoot`) or a silent no-op.
- **No input surface:** the menu reads only `connectionMessage`, `availableFarmhands`, `timedOut`. No network handler constructs a text-input menu, no vanilla password prompt exists, and the IP-field text never reaches the server. A pre-join back-channel must be out-of-band — e.g. Discord plus a per-connection code shown via type 11.
- **LAN `connectionId` is session-scoped, not a machine key:** `"L_" + RemoteUniqueIdentifier` (`LidgrenServer.cs:296-299`) hashes the client's ephemeral local port + MAC (Lidgren's `NetPeer.InitializeNetwork` — library source, not in `decompiled/`; the port is OS-assigned each launch because the client binds with port 0). Stable within one game session and its reconnects, fresh on every restart; the MAC cannot be recovered from it. Source IP (`conn.RemoteEndPoint.Address`) is the only cross-restart transport identifier on LAN, with all its NAT/shared-IP caveats.

**Why:** The message-type sweep and the Lidgren hash inputs were derived for the LAN farmhand-ownership investigation and are expensive to re-derive. The per-lever mechanics cost a long login-hold spike on top of that, because every attempt to polish the prompt hit an unseen wall: padding and off-left tricks to hide the `Strings\UI:` prefix all died on the x-clamp, "move the text up" was impossible, a show-a-mock-slot-then-reveal flow was killed by the latch, and dropping the still-at-menu client needed a forceKick. The recurring temptation all of this refutes: "surely there's some pre-join message that renders more UI / prompts for input / identifies the machine" — there isn't.

**How to apply:** Accept that custom status text carries the `Strings\UI:` prefix and sits from the vertical center down; don't design a mock-slot-then-swap flow (status-text hold **or** a click/reconnect); drop held clients with a type-23 forceKick, not `kick`. Don't key durable per-client state on the LAN connectionId — it dies at restart, so correlate out-of-band and bind to a synthetic `userID`, or accept source-IP semantics. If a design needs a richer pre-join channel, it must be out-of-band by construction, not a hunt for an unused message type.
