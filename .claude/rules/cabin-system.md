# Cabin allocation invariants

When editing cabin allocation, slot assignment, or new-game setup, the following invariants must hold:

1. **`BuildStartingCabins` is Harmony-patched out for EVERY strategy, and the interceptor is registered unconditionally with per-message gating.** `CabinManagerService`'s constructor registers the `BuildStartingCabins` disable-patch, the `locationIntroduction` message interceptor, and the farmhouse `UpdateTicked` monitor for all strategies; the handlers gate on `options.IsNone` per message/tick. Location DELTAS are deliberately not intercepted — cabin interiors are named `FarmHouse{guid}`, so a name-matched `Cabin` delta hook can never fire, and server-side warp rewrites (`Relocate`, `!cabin reset`, the commit pass) mutate the global interior's warps, which replicate to clients as deltas. Two traps make that delta load-bearing and non-automatic: (a) a client **re-derives interior exit warps locally from the building's position while deserializing a location introduction** (`buildings.OnValueAdded` → `Building.updateInteriorWarps`, no `IsMasterGame` guard), so the introduction's own warp targets are always clobbered client-side and only a post-introduction delta restores them; (b) a `NetInt` equal-value write is a silent no-op (no delta), so a rejoin whose targets are already correct server-side would never get that delta — `CabinExtensions.SetWarpsToFarm` therefore bounces through a differing value to force one. A delta's value is also invisible on the client until the netcode interpolation window elapses (`InterpolationWait`, 15 client ticks — 3s at `CLIENT_TPS=5`), which is why warp-walking E2E tests gate on the client's own warp copy (`/actions/location_warps`) before walking. Constructor-time gating on the boot strategy is wrong because the strategy can change in-process (settings-file `/reload`, migration commit). Consequently `Game1.startingCabins` (set before `loadForNewGame()` in `GameCreatorService.CreateNewGame`) is never consumed headless — the mod places all cabins itself (invariant 9 for `None`; hidden-location builds for the stacked strategies). Don't confuse it with `difficultyModifier`, which genuinely must be set *after* `loadForNewGame()` (also in `CreateNewGame`).
2. **`DELETE /farmhands` must call `EnsureAtLeastXCabins(minEmptyCabins=1)` after removing a farmhand and its cabin building.** Otherwise the next join sees an exhausted cabin pool.
3. **`sendAvailableFarmhands` (Harmony patched) must call `EnsureAtLeastXCabins` before filtering.** Rapid delete/rejoin cycles otherwise exhaust all cabins.
4. **Concurrent joins need `SlotSelectionGate` (a `SemaphoreSlim`).** `FarmhandMenu` only exposes ONE uncustomized slot at a time (index 0); two clients racing without the gate both claim index 0 and one is kicked.
5. **Lobby cabins live at tile (-21,-21); the regular cabin stack is at (-20,-20).** Don't conflate these coordinate sets when patching cabin placement logic.
6. **`buildStructure` already creates the farmhand on master — don't add an explicit `CreateFarmhand` after it.** `NetworkTweaker.SendBuildingConstructedEvent_Prefix` calls `location.OnBuildingConstructed(building, who)` directly, which runs `performActionOnConstruction → Cabin.CreateFarmhand` for ownerless cabins. Lobby cabins must remain ownerless by design — `CleanupLobbyCabinInterior` deletes the master-created farmhand.

7. **A disconnecting farmhand has TWO Farmer objects — a disconnect-hook clear must write `farmhandData[uid]`, not `cabin.owner`.** A connected farmhand exists as the live `Game1.otherFarmers[uid]` AND the persisted `netWorldState.Value.farmhandData[uid]`. `Cabin.owner` resolves via `Game1.getAllFarmhands()` (`Game1.cs:10967`) to the live copy for an **active** farmhand, the persisted entry for an **inactive** one. On the `GameServer.playerDisconnected` postfix the farmer is still active → `cabin.owner` is the live copy, which `removeDisconnectedFarmers` discards later in the same tick (vanilla `saveFarmhand` has already `CloneInto`'d its state, stuck userID included, into `farmhandData[uid]`). So clearing `cabin.owner.userID` from a disconnect hook does **nothing durable** — write `farmhandData[uid]` (value-writes on its `NetString`/`NetField` members aren't `FieldDict` mutations, so [`netdictionary-public-surface.md`](netdictionary-public-surface.md) holds). At `OnSaveLoaded` no farmhand is active, so `cabin.owner` already IS the `farmhandData` entry — only the disconnect path diverges. A "clear" means BOTH markers: the `userID` stamp AND the `FarmhandOwnershipService` owner record (the gate recorder maps a slot at approve even when the client stamps nothing, so a map-only claim is real).

8. **Abandoned-claim cleanup needs BOTH a disconnect heal AND a load-time sweep — the sweep is not redundant.** A stuck `userID` on an uncustomized-but-**homed** farmhand survives save→reload: vanilla `ResetFarmhandState` (`NetWorldState.cs:757`) clears `userID` only in its `else` branch (`:771`), reached when `TryAssignFarmhandHome` returns false (no resolvable home). It returns true when `getLocationFromName(homeLocation.Value) is Cabin` — and an abandoned slot's `homeLocation` points at its own still-existing cabin, so the clear is skipped. The only vanilla `userID.Value =` write-sites are the stamp (`Client.cs`), `/unlinkPlayer` (`ChatCommands.cs`), and this home-missing else; no other clear-path exists. So a restart does **not** self-heal a stuck-but-homed claim — `CabinManagerService.ClearAbandonedCabinClaimsOnLoad` (from `OnSaveLoaded`) is required alongside the disconnect heal. An abandoned claim is `!isCustomized && (stamp != "" || owner record exists)` — both the stamp and the ownership-map entry are cleared together (`TryClearAbandonedClaim`); an empty stamp must NOT early-return, or map-only claims strand. Vanilla `/unlinkPlayer` clears only the stamp — `farmhand release` is the supported operator path.

9. **Don't trust vanilla `BuildStartingCabins` placement on the headless `None` new-game — place via the mod's own path, and assert exact counts.** Vanilla `BuildStartingCabins` picks the correct positions and `buildStructure(skipSafetyChecks: true)` adds the building unconditionally (`GameLocation.cs:16718-16736`), yet those cabins don't survive `loadForNewGame`'s map-realization (farm reconstructed, `locations` rebuilt around `Game1.cs:3313/3366/3367`; `BuildStartingCabins` runs at `:3372` via `Farm.AddDefaultBuildings`) — so vanilla-placed `None` cabins silently vanish and only the `EnsureAtLeastXCabins` backfill minimum survives. Fix: `GameCreatorService.CreateNewGame` calls `EnsureAtLeastXCabins` for `None` with the full frozen count — `min(designated positions, MaxPlayers)`, persisted as `PersistentOptionsSaveData.NoneCabinCount`; `StartingCabins` is ignored under `None` — placing via the mod's `BuildNewCabinVisible` → `FarmCabinPositions` + `CreateCabinBuilding` path, which checks the interior was created and retries via `ReloadBuildingData` (the defense vanilla lacks). `EnsureAtLeastXCabins` clamps `None` growth to that frozen cap (`GetNoneCabinCap`); the save-import finalizer builds directly and is exempt. A staged migration commit to `None` re-freezes `NoneCabinCount` at the final visible non-lobby count (invariant 11). Designated-position count is 7 on Standard **per layout**: every vanilla farm map authors BOTH marker sets (tile 29 = nearby, tile 30 = separate; 14 markers total on Standard), and `FarmCabinPositions` mirrors vanilla's `Game1.cabinsSeparate` selection — `cabinsSeparate` is NOT save-persisted, so `OnSaveLoaded` restores it from the settings file's `CabinLayoutNearby` before any consumer runs. Merging the two sets silently doubles the None ceiling (the exact-count test caught exactly that). `None` count tests MUST assert the exact count, never tolerant bounds. A settings-file switch in a materializing direction (`RequiresStagedMigration`: stacked→`None`, `FarmhouseStack`→`CabinStack`) on an existing save is rejected at load (gated on `hiddenCabins.Count > 0` so a fresh `None` game doesn't false-trip); the supported path is the staged `cabins migrate` flow.

10. **An uncustomized farmhand can be silently DELETED when a save loads — the game's re-homing pass hands its cabin to another farmhand, no matter what stamps or ownership records it carries.** At load, `ResetFarmhandState` re-checks every farmhand's home; one whose cabin doesn't resolve is assigned another cabin. `Cabin.CanAssignTo` allows taking a cabin whose current farmhand is uncustomized — `Farmer.isUnclaimedFarmhand` is just `!IsMainPlayer && !isCustomized` (`Farmer.cs:1558`), blind to stamps and the ownership map — and `Cabin.AssignFarmhand` then calls `DeleteFarmhand()` on the displaced one (`Cabin.cs:92-104` → `FarmerTeam.DeleteFarmhand` → `farmhandData.Remove`). This fires routinely — but don't count `cabin_owner_changed` events as the evidence: that event is a 1 Hz snapshot diff keyed by tile (`ApiService`), and every hidden cabin shares (-20,-20), so a hidden-stack entry can also be mere enumeration-order noise rather than a real reassignment. Any state keyed to an uncustomized farmhand's uid — an ownership record, an operator pre-assignment — evaporates with the farmhand unless the slot is protected: `FarmhandOwnershipService.CanAssignTo_ProtectOwnedSlot_Postfix` narrows `CanAssignTo` so a cabin whose farmhand has an ownership record may only be assigned to that same farmhand (released markers and swept claim records leave no record, so freed slots stay reusable). Corollary: a cabin-backfilled farmhand exists ONLY in memory until the next save — binding anything to its uid without persisting the world (`SaveNow`) leaves a record whose farmhand doesn't exist on disk, and the next load's orphan-drop removes it (`farmhand rebind`'s save-always `PersistenceNote` exists for exactly this).

11. **Staged strategy migration (`cabins migrate`) is commit-at-end and never destructive — its four invariants must all hold.** (a) The old strategy stays live for the whole staging window; the flip happens only at commit, which must write BOTH the persisted strategy AND `server-settings.json` (`ServerSettingsLoader.SetCabinStrategy`) or the next `SyncFromSettings` reverts it. (b) All staging placement (auto and manual) is `CabinPlacementValidator`-gated with NO `ClearTerrainBelow` — never use `Building.Relocate` (it clears terrain); that non-destructiveness is what makes abort trivially safe. (c) Migration-placed cabins (`CabinMigrationState.PlacedCabinIndoorNames`, matched by interior `NameOrUniqueName`) are exempt from BOTH bulk movers (`SyncExistingCabins` MoveToStack sweep and `ApplyStrategySwitch`), and `DetectAndApplyStrategySwitch` refuses file-driven strategy changes while a record is active. (d) "Remaining" is always computed live (hidden non-lobby count for →`None`; the re-validated stack spot for FarmhouseStack→CabinStack) — a join during staging legitimately raises it, and commit refuses while it is nonzero. The record and staged positions are save-persisted only at the next game save: commit runs `SaveNow` when no farmhands are online, and the load-time pre-commit heal in `DetectAndApplyStrategySwitch` reverts the strategy (and the commit's `NoneCabinCount` freeze) when a pre-commit world reloads under an already-flipped strategy. When even the record never reached a save (start and commit in one unsaved window) — or a stacked-strategy save is imported onto a None-configured server — `ReconcileHiddenCabinsUnderNone` is the load-time backstop: None must never run with hidden non-lobby cabins (invisible, dead warps, still counted against the cap), so it places them at designated spots validator-gated.

**Why:** Each invariant traces back to a real cabin-allocation bug — the filter-before-ensure bug caused new joiners to see "server full" after a few rotations; `SlotSelectionGate` was added after two clients collided on index 0 and one got kicked. Invariant 6 documents the contract established by the `SendBuildingConstructedEvent_Prefix` patch: master runs the construction handler exactly once, peers don't run it at all. Invariant 9's diagnosis took 5 instrumented probe runs — all inputs correct and `buildStructure` called, yet 0 `isCabin` buildings at postfix; tolerant `>= 1` / `<= 6` assertions hid the silent-yields-1 bug for a long time.

**How to apply:** When editing `CabinManagerService.cs`, `GameCreatorService.cs`, `GameLoaderService.cs`, or any code calling `loadForNewGame()` / `BuildStartingCabins` / `EnsureAtLeastXCabins`, walk through all eleven invariants above. The map-position reference for `BuildStartingCabins` (tile 29/30 in Paths layer) is in [`docs/developers/architecture/game-engine-notes.md`](../../docs/developers/architecture/game-engine-notes.md).
