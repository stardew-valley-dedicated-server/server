# Map any "make the client do X" feature onto the verified server→client primitives, or change the design

Farmhand clients are unmodded vanilla (`CLAUDE.md`), so any feature that needs a client to move, see, or do something must map onto net-synced server-authoritative state or one of these verified vanilla messages — there is nothing else:

1. **Join-time arrival placement** (message 3, `GameServer.sendLocation(peer, location, force_current: true)`) — the server picks where a joining farmhand lands. `readActiveLocation` applies it by setting `Game1.currentLocation` and `Game1.player.currentLocation` directly whenever no client-initiated `locationRequest` is pending (`Multiplayer.cs:1349-1370`). Vanilla drives it from the farmhand's `disconnectLocation` (same-day reconnect) or `lastSleepLocation` (`GameServer.cs:585-600`), both server-writable `Farmer` fields. Fires inside `checkFarmhandRequest`'s approve path — **join-time only**, not a mid-session lever.
2. **Passout message** (`Multiplayer.passout`, message 29) — the only server-initiated warp of an *already-joined* player: the client fades and warps to the named location+tile (`Farmer.performPassoutWarp`, `Farmer.cs:5841`). **Fee-gated**: unless the player's *source* location is `FarmHouse`, `IslandFarmHouse`, `Cellar`, or map-flagged `PassOutSafe`, the client charges the pass-out fee and sends pass-out mail (`Farmer.cs:5869-5877`). `IslandFarmHouse` is a sibling of `FarmHouse`, not a subclass — both derive from `DecoratableLocation`. `FarmerExtensions.WarpHome` is fee-free only because its callers have the player standing in a lobby cabin when the message arrives — its docstring doesn't say so.
3. **`GameLocation.warps` mutations** are net-synced and client-effective: the lobby's exit-warp removal (`LobbyService.cs`) and the hidden-cabin exit rewrite (`CabinExtensions.SetWarpsToFarmFarmhouseDoor`) are production proof. Per-location, shared by all players — no per-player warp targets on a shared location.
4. **Forced events (message 4) cannot serve as warps**: the client resolves the event id against its *own* content (custom events don't exist there) and returns the player to the pre-event location afterward (`Multiplayer.cs:1616-1642`).
5. **Message 5 (`warpFarmer`) is client→server only** — it is absent from the client's `processIncomingMessage` switch, so the server can *observe* every client warp (`GameServer.cs:698-724`) but not drive one with it. Observation is free; intervention is not.

**Why:** The per-player-farms investigation first designed farmhand warp routing around client-side patching, which the vanilla-client fact invalidates wholesale. The passout fee gate is the sharpest residual trap: `WarpHome`'s comment ("does a screen fade and then warps the player") reads like a general-purpose teleport, and reusing it while the player stands outdoors silently charges them the pass-out fee and sends pass-out mail.

**How to apply:** When a design needs vanilla clients to change location or behavior, map it to a primitive above before writing anything; if none fits, the design changes, not the client. Reach for (1) when the requirement is "this player starts somewhere specific" and for (2) only when an already-joined player must move — and before reusing `WarpHome`/the passout message, check what location type the player occupies when it arrives, since from outdoors it costs fee + mail. Sibling of [`harmony-patch-reachability.md`](harmony-patch-reachability.md), which covers why client-side patching is off the table at all, and [`prejoin-control-surface.md`](prejoin-control-surface.md), which covers the pre-join surface.
